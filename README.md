# Procedural Island Generation

A procedural 2D island generator written in **C++**, rendered with **SFML**, with both **serial** and **Intel oneTBB parallel** implementations. It creates islands with irregular coastlines, lakes, terrain transitions, trees, bushes, and forest-like clusters. All of the pixel art used to build the maps was drawn by me.

[**Watch the generation demo on YouTube**](https://youtu.be/HD4ZddbgSeU) - 15 different maps, generated five times each at widths of 20, 120, and 520 tiles.

![A procedurally generated island with trees, beaches, and lakes](docs/images/Screenshot%202026-10-26%20144217.png)

## How this project started

My interest in procedural generation started long before this university project. A few years earlier, I was experimenting with a similar idea in **Unity and C#**. I wanted to build a world that could create itself, and I eventually found a tutorial introducing the **Drunken Walker** approach to map generation.

At first, generating a patch of green land was relatively easy. What came after it was much more difficult. I wanted shores, water, trees, bushes, and transitions that actually looked like parts of the same environment. I kept adding rules, testing different ideas, running into indexing problems, and trying to solve them on my own rather than immediately looking up every solution. The code gradually became a mess of special cases and `if`/`else` statements. At one point, I honestly wondered whether I had found a programming problem I simply couldn't solve.

That first experiment never became the larger project I imagined, but I learned a lot from trying to make it work.

When I later took **Parallel Programming** at the **Faculty of Technical Sciences, University of Novi Sad**, we could choose our own exam project as long as it involved parallelization and a report. I immediately thought of returning to this idea. It gave me a reason to build the generator again, this time in **C++**, with a clearer structure and a separate parallel implementation to explore.

This version follows the spirit of the original experiment, but replaces much of the complicated tile-selection logic with a more systematic **neighborhood-mask** approach. I also drew the terrain and vegetation sprites myself, which made the result feel like a project of my own rather than just an algorithm on a grid.

Drawing the sprites was a big part of the process for me. I wasn't just trying to produce an abstract map made of differently colored cells. I wanted to see beaches connect to the sea, small lakes appear between patches of grass, and clusters of trees turn an empty island into something that looked alive. Having to make those pieces fit together also forced me to think much more carefully about how the generator represented its surroundings.

### The bigger idea I still have in mind

The islands were never supposed to be the end goal. I have always been interested in building some kind of **ecosystem simulation**, with creatures, behaviors, evolution, inheritance, and natural selection. A procedural world would have been the starting environment for those systems.

I did not get as far as implementing the ecosystem or evolutionary simulation, either in the original Unity experiment or in this C++ project. **This repository is an island generator, not an ecosystem simulator.** It is the part of that bigger idea I managed to finish and develop into a standalone project.

## What it generates

- **Configurable island shapes** using randomized Drunken Walkers, with parameters controlling map coverage and walker behavior.
- **Coastlines and beaches** formed around the landmass.
- **Inland water** distinguished from the surrounding ocean.
- **Terrain textures and transitions** selected using neighborhood bitmasks rather than a large set of manually written cases.
- **Trees and bushes** with different appearances, heights, and spatial clustering to create patches of woodland and vegetation.
- **Maps of different sizes**, with the height calculated automatically from the width to follow the window's approximately 16:9 aspect ratio.

The map is generated once when the application starts and is then displayed using SFML. This is a procedural-generation demonstration, not a complete game or interactive map editor.

## Serial and parallel implementations

The repository contains two versions of the same overall generation pipeline:

- **`Serial/`** uses ordinary sequential loops and serves as the baseline implementation.
- **`Parallel/`** uses **Intel oneTBB**, including `parallel_for`, `blocked_range`, and `blocked_range2d`, for selected pieces of work that can be divided across cells or walkers.

In the parallel version, independent parts of water classification, terrain decoration, and sprite preparation can be split into tasks. Walker movement is parallelized, while updates that could conflict on the same map cell are handled separately. Other work remains sequential, including changes to the walker collection, parts of shoreline creation, vegetation placement, and SFML drawing where ordering matters.

Working on both versions helped me understand an important limitation of parallel programming: **more parallel code does not automatically mean a faster program**. Some stages have dependencies, some have too little work to justify scheduling overhead, and some expensive stages are still sequential.

I originally chose this topic partly because I thought a parallel implementation would make a huge difference. In practice, it wasn't that simple. The result depended on which stages were expensive for a particular generated island, not merely on how many loops I had parallelized. That was a useful outcome of the course project in its own right, even if it wasn't the dramatic speedup I had expected.

The original exam [documentation](docs/Documentation.pdf) includes timing measurements from the earlier implementation. Those results should be treated as exploratory: islands are randomly generated, their complexity changes between runs, and the code was subsequently adjusted. I have not included a new speedup claim here because a reliable comparison would require controlled random seeds, repeated runs, and separate measurements of the generation stages.

## Technologies and implementation

| Technology | Role |
| --- | --- |
| **C++17** | Generation algorithms and application logic |
| **SFML 2.6.2** | Windowing, sprites, textures, and rendering |
| **Intel oneTBB** | Task-based parallel loops and concurrent containers |
| **Visual Studio / MSVC** | Windows solution and project configuration |
| **vcpkg** | oneTBB dependency management |
| **Custom pixel art** | Terrain, coastlines, water, trees, and bushes |

The `Map` class coordinates the generation stages and terrain representation. Separate `Tree` and `Bush` classes share a common `Vegetation` base class. Tile sprites use neighboring tile information to select appropriate textures, while the final vegetation drawing order accounts for overlapping objects.

## Building and running

This project is configured for **Windows and Visual Studio**, using the **MSVC v143 C++ toolset**. SFML 2.6.2 is included under `third_party/`; oneTBB is managed through vcpkg.

1. Open `Procedural-Island-Generation.sln` in Visual Studio with C++ desktop development tools installed.
2. Make sure vcpkg is installed and integrated with MSBuild. In a Developer PowerShell, `vcpkg integrate install` sets up user-wide integration; from the repository root, `vcpkg install --triplet x64-windows` installs the manifest dependencies.
3. Select **Release | x64**.
4. Right-click **Serial** or **Parallel** in Solution Explorer and choose **Set as Startup Project**.
5. Build and run the selected project.

To experiment with the generator, change `mapWidth` and the `Map` constructor parameters in `Serial/Ecosystem simulation.cpp` or `Parallel/Ecosystem simulation.cpp`. The height is calculated from the width, and the constructor exposes land coverage, walker count, tree density, forest clustering, bush density, and bush clustering.

**Note:** The application loads its images using relative paths such as `../Assets/Grass`. Run it with the corresponding project directory as its working directory, or adjust the working directory in Visual Studio if the textures cannot be found.

## Final thoughts

I started with the idea of generating a little island and kept finding new things I wanted to add. The original Unity experiment was messy, and this C++ version is still not the ecosystem simulation I eventually want to build, but it represents a meaningful step between those two ideas.

What I value most about it is not a particular performance number. It is the combination of **algorithmic problem-solving, C++ programming, selective parallelization, and art I drew myself**, all working together to produce a different little world every time I run it.
